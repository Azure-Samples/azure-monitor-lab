# P1 native OTLP logs — experimental, default-off opt-in

With Stage A and the Linux VM in Stage B enabled, setting `advancedConfiguration.telemetryIngestion.enableNativeOtlp=true` in `lab.config.json` opts the scripted one-shot deployment into a dedicated native logs DCR and a pinned Collector on the existing Ubuntu VM. `scripts/deploy-native-otlp.ps1` verifies the exact VM, DCR immutable ID, DCE endpoint and identity, grants that VM's managed identity **Monitoring Metrics Publisher on the native DCR only**, and installs a checksum-pinned Collector Contrib v0.148.0 service with a loopback-only OTLP receiver. The feature remains experimental: provisioning alone does not establish that the documented native stream and endpoint spellings interoperate in your region, or that any record arrived. No automatic test traffic is sent.

The fixture is generated by `scripts/telemetry-ingestion-helpers.ps1` (`New-TelemetryIngestionFixture`); no JSON fixture file is required. `scripts/send-telemetry-otlp.ps1` serializes the 100 records as an actual OTLP `ExportLogsServiceRequest` in binary protobuf. It sends HTTP/protobuf only to a loopback Collector; there is **no JSON bridge** and it does not use the P0 JSON DCR. The sender normalizes its own copy of `TimeGenerated` to UTC ISO 8601 **six fractional digits** and sets OTLP `time_unix_nano` to the corresponding microsecond-precise instant; it does not change the shared fixture helper. `RunId`, `EventId`, `SampleSetId`, `TimeGenerated`, `Severity`, `Workload`, `Message`, `SyntheticUser`, `DebugField` are **record** attributes; `service.name=telemetry-ingestion-demo` is a **resource** attribute; `telemetry-ingestion.fixture` version `1.0.0` is the instrumentation scope. Severity numbers are Error=17, Warning=13, Debug=5. The fixture's synthetic user is deliberately non-real, but do not use production identities: this path does not apply the JSON DCR redaction policy.

The Collector config pins **OpenTelemetry Collector Contrib v0.148.0** (or a distribution built from that exact release with `azure_auth`, `otlp`, `batch`, and `otlphttp`). This version supports `azure_auth.managed_identity: {}`. The receiver binds only `127.0.0.1:4318`; deploy this Collector only by separate opt-in on an Azure VM with a dedicated system-assigned managed identity. Do not bind the existing AMA listeners or change any lab exporters. The identity requires **Monitoring Metrics Publisher on the native OTLP DCR**, and the host needs HTTPS access to the DCE. The logs endpoint must be taken from the Application Insights **OTLP Connection Info**, or constructed from the *dedicated native* DCR immutable ID and DCE `logsIngestion.endpoint`:

```
https://<logs-dce-domain>/datacollectionRules/<otlp-dcr-immutable-id>/streams/Microsoft-OTLP-Logs/otlp/v1/logs
```

Set `AZURE_MONITOR_OTLP_LOGS_ENDPOINT` to the complete URL **in the Collector process environment**, not in a committed config. `azure_auth` requests `https://monitor.azure.com/.default` and attaches an Entra bearer token to `otlphttp` requests; the sender's loopback hop has no Azure token. If running the Collector on an Arc/K3s node instead of Azure VM, replace the managed-identity configuration with an explicitly provisioned supported workload identity after verifying its credentials and DCR assignment. Never commit credentials.

**Provisioning compatibility gate:** The P0 JSON DCR cannot receive this binary stream. The native DCR uses the published `Microsoft-OTel-Logs` direct data source **without** `kind: Direct`: Azure reserves that kind for Log Ingestion API rules and rejects OTLP `directDataSources` with it. The documented OTLP URL names its endpoint stream `Microsoft-OTLP-Logs`; this discrepancy is not verified by offline compilation. If the deployed DCR or URL rejects the stream, stop and resolve the contract with a small approved probe rather than relabeling the JSON `Custom-TelemetryIngestion` stream or reporting success.

Local-only bounded offline exercise (PowerShell 7):

```powershell
pwsh -NoProfile -File scripts\tests\telemetry-otlp-edge.Tests.ps1
pwsh -NoProfile -File scripts\send-telemetry-otlp.ps1 -Mode Otlp -OutFile workloads\telemetry-ingestion\otel\sample.pb
# Delete sample.pb after inspecting it; the attributes contain the synthetic fixture.
```

After **separate approval and provisioning** of the native OTLP resources, identity and Collector, establish an SSH local port forward to VM loopback port 4318; never expose this receiver publicly. Send once through that local port:

```powershell
pwsh -NoProfile -File scripts\send-telemetry-otlp.ps1 -Mode Otlp -RunId ([guid]::NewGuid())
```

The sender's HTTP 2xx proves only local Collector acceptance, **not** export or cloud ingestion. Query the actual LAW (not the JSON custom table), filter on the printed RunId, compare all 100 distinct IDs and 20/30/50 severity counts, and inspect resource/scope/record fields separately:

```kusto
OTelLogs
| where TimeGenerated > ago(2h)
| where tostring(Attributes.RunId) == "<printed-run-id>"
| project TimeGenerated, EventId=tostring(Attributes.EventId),
          SeverityText, ServiceName, ResourceAttributes, ScopeName, ScopeVersion, Attributes
| order by EventId asc
```

Check `ScopeName == "telemetry-ingestion.fixture"`, `ScopeVersion == "1.0.0"`, `ServiceName == "telemetry-ingestion-demo"`, and record keys in `Attributes`; check `ResourceAttributes` **independently**, as the pipeline documentation warns that `ServiceName` alone is not proof the resource bag was saved. No cloud ingestion was performed in this change.

Native logs/traces go to Log Analytics, metrics go to an Azure Monitor workspace; this sample intentionally emits **logs only** and makes no traces/metrics or custom-table fan-out claim. Direct OTLP-to-P0 `Custom-TelemetryIngestion` is **not configured or verified**.
