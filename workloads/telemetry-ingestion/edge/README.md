# P2 edge and combined — opt-in Arc K3s preview

**Default-off:** the normal scripted deployment does not install K3s, connect Arc, or provision the pipeline. The separate `advancedConfiguration.stageToggles.enableStageAzureMonitorPipeline` opt-in in `lab.config.json` invokes `scripts/deploy-azure-monitor-pipeline.ps1` after the one-shot lab setup, on the *existing lab Linux VM*. It requires explicit owner approval, an explicitly selected VM SKU with at least four vCPUs and 16 GiB total memory, available host capacity, Arc onboarding permission, provider/region support and expected egress. It does not create another VM or modify AMA. The flag is independent of the JSON telemetry-ingestion stage; the portal and Terraform paths do not automate this VM/Arc step. A prior live deployment accepted the implicit-TLS DCRs, but ingestion is not verified.

Merge the relevant values into your existing `lab.config.json` (do not replace unrelated settings):

```json
{
  "advancedConfiguration": {
    "compute": { "linuxVmSize": "Standard_D4as_v5", "windowsVmSize": "Standard_EC2as_v5", "deployLinuxVm": true },
    "stageToggles": { "enableStageB": true, "enableStageAzureMonitorPipeline": true }
  }
}
```

The SKU is an **example**, not a size automatically chosen by the flag; verify its availability and quota. On an existing lab, changing `linuxVmSize` in the main deployment can resize/restart the **Linux** VM, interrupt monitoring, and increase costs; `windowsVmSize` remains unchanged. The legacy `vmSize` applies to both only when the OS-specific overrides are omitted. Do not opt in during another person's demo. Bootstrap requires the VM to be running, provisioned, and VM Agent ready (check `az vm get-instance-view` under `instanceView`); VM power state alone is insufficient. When the pipeline opt-in is enabled, bootstrap registers missing `Microsoft.Kubernetes`, `Microsoft.KubernetesConfiguration`, and `Microsoft.ExtendedLocation` providers in the selected subscription and waits for registration; the operator needs subscription provider-registration permission. It installs the local `k8s-extension` Azure CLI extension if missing, without upgrading an existing version. The VM's system-assigned identity must have the scoped **Kubernetes Cluster - Azure Arc Onboarding** role on the lab resource group before the cluster connection; the deploying identity also needs VM Run Command, Arc extension, DCR, DCR association, deployment and role-assignment permissions. The opt-in installer adds Azure CLI and the `connectedk8s` extension from Microsoft, plus checksum-verified Helm and K3s binaries, to the existing VM when missing. Confirm outbound HTTPS to the Microsoft package repository, GitHub release assets, Helm downloads and Arc/pipeline endpoints; a failed prerequisite stops bootstrap rather than silently skipping Arc. Only the extension's system-assigned identity receives Monitoring Metrics Publisher on the scenario-owned dataflow DCR.

The Arc extension catalog also requires the subscription's separate `Microsoft.KubernetesConfiguration/ExtensionTypes` preview **feature** to be `Registered`; provider registration alone does not enable it. An authorized operator can request it with `az feature registration create --namespace Microsoft.KubernetesConfiguration --name ExtensionTypes --subscription <sub>` and check `az feature show --namespace Microsoft.KubernetesConfiguration --name ExtensionTypes --subscription <sub> --query properties.state -o tsv` until it reports `Registered`. This subscription-wide preview enrollment is not performed automatically. Re-register `Microsoft.KubernetesConfiguration` after enrollment to propagate it; the catalog API may still return `InvalidResourceType` briefly. Wait for the preview catalog and its pinned version to respond before retrying; do not bypass either check.

The Linux VM's system identity must also have `Kubernetes Cluster - Azure Arc Onboarding` at the lab resource group (or inherited) scope; an opted-in deployment does not grant it automatically. Check with `az role assignment list --assignee-object-id <vm-principal-id> --scope <resource-group-id> --include-inherited`. Azure CLI rejects combining `--scope` with `--all`. If the role is missing, an authorized operator can grant **only** that role at the lab resource group; the bootstrap prints the exact command and stops before Run Command.

The installer does not require host port 4317 to be free: an existing MetricsExtension listener on loopback is independent of the pipeline's Kubernetes-pod Syslog receiver on 6514. Do not stop or reconfigure the monitoring extension to clear a `ports` denial. The installer still checks host listeners on 6514, 6443, 10250, 2379 and 2380 before installing K3s.

The scenario-owned K3s service now binds the kubelet to the VM's private IPv4 address, not `127.0.0.1`: the Kubernetes API server connects to the node's `InternalIP` on 10250 for pod logs and port-forwarding. An earlier installer bound the kubelet only to loopback, causing `kubectl logs` to fail with a 502 when the API server dialed `<node-private-ip>:10250` even while the node was Ready. Existing owned services are **not** changed or restarted on rerun; preflight reports `PIPELINE_DENIED:k3s` until the unit and running listener use the private IP. This is separate from the missing managed certificates.

For an existing scenario-owned VM with that exact old unit, arrange a maintenance window: restarting K3s interrupts its Arc/pipeline pods. Confirm the node `InternalIP` is still the VM's private IP and that neither the NSG nor host firewall permits **public** access to 10250; do not add an inbound rule. Check the owner marker and original unit before proceeding. On `vm-amlab-lin`, if its node IP remains `10.50.1.5` and the unit has exactly the old `ExecStart` from this repository:

```bash
sudo test -f /etc/rancher/k3s/azure-monitor-lab-owner
sudo systemctl cat k3s
sudo ss -lntp '( sport = :10250 )'
sudo cp -p /etc/systemd/system/k3s.service /etc/systemd/system/k3s.service.before-private-kubelet
sudoedit /etc/systemd/system/k3s.service
# Change only --kubelet-arg=address=127.0.0.1 to --kubelet-arg=address=10.50.1.5
sudo systemctl daemon-reload
sudo systemctl restart k3s
sudo systemctl is-active k3s azuremonitoragent
sudo ss -lntp '( sport = :10250 )'
sudo env KUBECONFIG=/etc/rancher/k3s/k3s.yaml /usr/local/bin/k3s kubectl get nodes -o wide
```

Verify the kubelet listens on `10.50.1.5:10250`, the node is Ready, and `kubectl -n default logs deployment/azure-monitor-pipeline-controller-manager --all-containers=true --tail=10` no longer returns a kubelet 502. If the restart fails, restore the saved unit, run `systemctl daemon-reload` and restart K3s again; investigate before attempting another deployment. Use the actual current private IP rather than `10.50.1.5` if the VM address has changed, and review the scenario-owned K3s config before modifying it. Do not restart cert-manager, Arc agents or AMA to work around the log error.

If the remote `install` stage fails, it reports only a bounded stage code (for example `identity-login`, `identity-account`, or `arc-connect`), not Azure CLI output. Check the scenario-owned K3s service and Arc cluster status before retrying: install can leave K3s running even if the cluster connection has not completed. Do not remove the owner marker or restart monitoring agents to force a retry.
The Arc cluster's VM-ownership tag is `monitor-lab-edge-vm`; Azure reserves tag-name prefixes such as `azure`, so do not rename it to a reserved prefix.
Extension readiness checks require successful provisioning and a reported `currentVersion` (the pipeline must report pinned `0.1.7`), plus the pipeline identity. The extension ARM response may omit `installState`; missing or mismatched installed versions still stop Syslog deployment. Verify the Arc agents, cert-manager, and pipeline controller are ready in Kubernetes before claiming live operation.
On reruns, bootstrap uses the Arc cluster's detailed ARM response for ownership and health: `az resource list` can omit its provisioning and connectivity properties. It also lists extensions and DCR associations at the connected-cluster scope and reads matching DCRs individually, because generic resource-group listings may omit child resources or detailed properties. Foreign, orphaned, or unverified partial resources still stop the run.
The pipeline-settings DCR association name must begin with `pipelineSettings-`; the template uses `pipelineSettings-<prefix>-settings-assoc`. If deployment created the four scenario DCRs and other associations before that association failed, a rerun verifies each existing resource and creates the missing settings association without deleting or renaming unrelated resources. Orphan associations, mismatched DCR configuration or foreign ownership still stop deployment.

Turning the flag back off **does not uninstall** K3s, disconnect the Arc cluster, delete DCRs/extensions, or undo a user-selected `vmSize` change. After a demo, review exact ownership before separately removing scenario DCR associations/role assignment/DCRs, the pipeline and certificate extensions, the scenario-owned Arc connected-cluster resource and its locally installed K3s service. Do not remove the shared lab VM, AMA, workspace, or another owner's Arc resources. Stop any port-forward; never expose the Syslog receiver on a public endpoint.

Assess the existing host without changes:

```powershell
pwsh -NoProfile -File scripts\setup-telemetry-ingestion-edge.ps1 -HostName <linux-vm-dns> -SshUser <ssh-user>
# -OptIn acknowledges a planning decision only; even with it, the script never installs anything.
```

The read-only SSH probe checks Linux/architecture/systemd, >=4 available CPUs, >=8 GiB *available* memory, >=20 GiB root free, DNS/HTTPS, listener ports, AMA and existing K3s/Arc tools. The VM Run Command preflight requires >=20 GiB free on `/` for a fresh K3s installation, or >=10 GiB on a rerun **only after** verifying the scenario owner marker, K3s files and binary checksum; `disk` means the applicable threshold was not met. An existing K3s install consumes root space, so retaining the fresh-install threshold would block safe reruns. `ama` means the guest `azuremonitoragent` service is inactive. Preflight does not print guest output or proceed to installation on denial or missing markers. A 30 GiB provisioned OS disk does not prove that 20 GiB is free. The probe cannot certify Azure Arc/K3s compatibility, actual DCE egress, storage IOPS, isolation or free capacity under workload; a failed check halts planning. Before a separately approved installation, confirm supported distro/version, K3s container networking/cgroup support, cert-manager, Arc Kubernetes regional support, disk and reserved resources, firewall/egress, collector/pipeline sizing, AMA health and rollback. `azcmagent` is an informational probe for Arc **server** and is **not** a substitute for Arc-enabled Kubernetes. Do not enroll the VM/cluster, install cert-manager/K3s, change network rules or stop AMA on the basis of this script.

`syslog-pipeline.arm.json` is a **preview configuration asset**: API `2025-05-11`, one `PipelineSettings` DCR, one separate pipeline dataflow DCR, two extension-scoped DCR associations, and a `Monitoring Metrics Publisher` role assignment. The scripted opt-in installs K3s, connects the cluster to Arc and uses `arc-pipeline-extensions.bicep` to add managed `microsoft.certmanagement` and `microsoft.monitor.pipeline` extensions (the pipeline is pinned to `0.1.7`, preview train, automatic minor upgrades disabled). It then deploys the Syslog ARM template. Workspace and DCR region must match and be pipeline-supported; the updated server-only TLS settings passed read-only ARM validation but are **not** active in the live DCR, nor has ingestion been proven. The template cannot be reused on an AMA DCR and is not the portal's legacy PipelineGroup model. Review the `what-if` for scenario-owned names and Azure role assignments before running any opt-in deployment.

**Actual edge policy** is the named `edgeDrop` transformation on `dataSources.syslog.fixtureSyslog`: `header.SyslogFullyFormed` normalizes RFC5424, then `transform.KQL` extracts `EdgeDrop=(true|false)` from `SyslogMessage`, keeps rows where the extracted flag `!= "true"` and removes its temporary column *inside the pipeline before cloud forwarding*. The opt-in `bypassFilter=true` ARM parameter changes only the standard Syslog route to `source`; use a **separate RunId**, verify propagation, then restore `bypassFilter=false`. The sender marks exactly Debug IDs `event-061`–`event-100` as `EdgeDrop=true`; IDs 001–060 are retained. The RFC5424 header carries the timestamp, and the message includes run/event/sample/severity/workload, with `SyntheticUser` masked and `DebugField` omitted **at the sender**; this is not a pipeline redaction demonstration.

The Syslog-to-`Syslog` route remains independent. When **both** `enableStageTelemetryIngestion` and `enableStageAzureMonitorPipeline` are true, an **experimental structured-Syslog combined route** additionally attaches two dataflow DCRs to the same private listener. The edge transform drops 40 marked Debug events; cloud DCR transforms project the remaining fields into the Stage 90 Operational Analytics table (50 Error/Warning IDs) and Diagnostic Analytics table (60 retained IDs). Each DCR has its own Arc association and publisher grant. The deploy script verifies both existing table IDs, schemas and plans before attaching these routes; Azure's child-table response can omit `type`. Offline ARM acceptance cannot prove pipeline/cloud transform composition or that the two custom tables receive any records. This is not native OTLP-to-custom-table fan-out or the 50/10 Auxiliary combined variant; never claim it until exact cloud IDs have been measured.

The K3s API binds to the VM's private IPv4 address so Arc pods can reach it; do not allow public ingress to Kubernetes port 6443. The receiver listens within the Kubernetes pod on 6514/TCP; the settings DCR selects managed `serverOnly` TLS, which requires the operator's server certificate and trust bundle. The published [TLS guide](https://learn.microsoft.com/azure/azure-monitor/data-collection/pipeline-tls) also documents `mode: disabled`, but the North Europe `2025-05-11` resource provider rejected it in live preflight (`InvalidPipelineSettings`; allowed: `serverOnly,mutualTls`). Do not retry that rejected template. **Never expose this port via public LoadBalancer/NodePort or a remote client.** For a local-only controlled test on the host, use a ClusterIP service and `kubectl port-forward --address 127.0.0.1 -n <extension-namespace> svc/<pipeline-service> 6514:6514` after inspecting the service selector `app.kubernetes.io/instance=<extension-name>,app.kubernetes.io/name=pipeline`. Limit access via namespace network policy; if remote clients are later required, use an approved gateway/network isolation and plan certificate trust and rotation.

After certificate reconciliation, identify the certificate's actual DNS SAN and the extension's server trust Bundle, then obtain the **public CA certificate** from its distributed ConfigMap as described in [automated certificate management](https://learn.microsoft.com/azure/azure-monitor/data-collection/pipeline-tls-automated#step-2-get-server-ca-certificate-for-client-validation). Do not export the server key. The Syslog sender connects only to `127.0.0.1` (a local port-forward or loopback SSH tunnel), but uses `-SyslogServerName` to validate the leaf's DNS name and `-SyslogCaFile` for private-CA trust. An invalid chain or name stops before sending records.

```powershell
# Offline: no Azure/SSH/network, decodes the emitted protobuf and checks 40 drop markers.
pwsh -NoProfile -File scripts\tests\telemetry-otlp-edge.Tests.ps1
# Only after certificates, pod, listener isolation and port-forward are Ready:
pwsh -NoProfile -File scripts\send-telemetry-otlp.ps1 -Mode Syslog -Profile Filtered -SyslogServerName <DNS-name-in-leaf-certificate> -SyslogCaFile <local-server-ca.pem> -RunId ([guid]::NewGuid())
# With both stages enabled and after recording the printed RunId, independently verify
# exactly 50 Operational and 60 Diagnostic IDs:
pwsh -NoProfile -File scripts\test-telemetry-ingestion.ps1 -SubscriptionId <sub> -ResourceGroup <rg> -Profile EdgeFanout -RunId <printed-run-guid>
```

The sender is bounded to 1–100 records; it emits UTC ISO 8601 timestamps with **six fractional digits** in the RFC5424 header. Each request prints generated count, marker count and **expected** retained count (not measured edge/cloud counts). For bypass use `-Profile Bypass` only when the deployed DCR's `bypassFilter=true`; the sender cannot inspect or change the DCR. For a higher-volume trial issue at most ten **separate** 100-record runs with fresh RunIds and explicit change approval; never start an infinite sender. Use new RunIds after every DCR profile change to prevent cross-profile contamination.

Evidence: record generated/marked IDs from the sender (100/40); inspect running pipeline pods and the settings/dataflow DCR associations, role assignment and config delivery **independently**. Obtain *actual* receiver/filter/export counters from the deployed extension's supported monitoring endpoint/logs before claiming edge counts (aggregate counters do **not** prove individual IDs); identify `100 received, 40 filtered, 60 forwarded` for the isolated RunId or mark that part unverified if per-run counters are unavailable. Query cloud `Syslog` for the RunId and enumerate all IDs, not just totals:

```kusto
Syslog
| where TimeGenerated > ago(2h)
| where ProcessName == "telemetry-ingestion"
| where SyslogMessage contains "RunId=<printed-run-id>"
| extend EventId = extract(@"EventId=(event-[0-9]{3})", 1, SyslogMessage)
| summarize Rows=count(), DistinctIds=dcount(EventId), Ids=make_set(EventId)
```

Filtered should have exactly IDs 001–060; bypass should have 001–100. Do not infer cloud success from local TCP writes, association existence, heartbeat, or accepted cloud request. To troubleshoot, check in order: VM capacity/AMA unchanged -> Arc/cert-manager/extension readiness -> settings and dataflow association + role -> private listener -> edge transform counters -> outbound network/DCE -> workspace query. A zero-row cloud query is a fault, not a successful filter test. Stop the local port-forward and restore the filtered DCR after experiments. Leave already existing VM/AMA/Arc infrastructure intact during cleanup.
